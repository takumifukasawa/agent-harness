# 0013: ペイロードの混入を「形で分かるものの検査」と「導入先にコミットさせない（lockfile 方式）」の二重で封じる

- 日付: 2026-10-16
- 状態: 採用（実装は [計画 payload-containment](../plans/active/payload-containment.md)）
- 改訂: 2026-10-16（同日、実装前）。禁止語リストをやめ、lockfile 方式に `install` と `source_commit` を足した。初版との違いは末尾の「改訂の経緯」

## 背景

2026-10-16 の公開前の精査で、ペイロード（`harness/`）の 2 か所（`scripts/doctor.sh` と `scripts/seed-case.sh` のコメント）に、導入先の実プロジェクトの名前が入っていたことが分かった。この 2 つは managed なので、`update` を通して他の導入先にも配られ、**そこでコミットされている**（入ったのは 0.8.0 なので、0.8.0 以降に `init` / `update` した導入先すべてが対象）。このリポジトリ側は履歴を作り直して消せたが、導入先の履歴に入ったものはこちらからは消せない。

問題はミスの種類によって重さが違うこと。

| ミスの種類 | 導入先でコミットする（〜0.11） | 導入先でコミットしない |
|---|---|---|
| スクリプトのバグ | `update` で直る | `update` で直る |
| 固有情報の混入 | **配った数だけ他人の履歴に残り、消せない** | `install` / `update` で消え、履歴に残らない |

検査をいくら強くしても、すり抜けた 1 回が消せないことは変わらない。逆に、コミットさせない形だけだと、混入そのものは減らない。

## 採用案

二重にする。

### 1. 形で分かるものは機械で止める（固有名は止めない）

リストが無くても形で見分けられるものだけを検査する。

- ユーザー名の入った絶対パス（`/Users/<名前>/`、`/home/<名前>/`、`C:/Users/<名前>/` など）
- メールアドレス（例示用の `example.com` / `example.invalid` や `noreply` 系は除く）
- トークンや鍵の形をした文字列（`ghp_`、`sk-`、`xox[bp]-`、`BEGIN ... PRIVATE KEY` など）
- 非公開のワークスペースへのリンク（Slack、Google Docs、claude.ai の会話やセッションなど）

検査する場所:

- このリポジトリの pre-commit。ペイロードに限らず**全ファイルとコミットメッセージ、`git config user.email`** を見る。今回公開されたものの大半は、配らない `docs/` と作者のメールアドレスだった
- `init` / `update` / `install` で導入先へ書き込む直前
- `upstream` で導入先から戻すとき

**会社名・プロジェクト名・ゲーム名のような固有名は機械では止めない。** リストが無ければ見分けられず、リストを作ればそれ自体が漏らしたくない名前の一覧になる。固有名は 2 で「すり抜けても導入先に残らない」形で受け、版を上げる前に人かエージェントが通読する（2026-10-16 の精査の手順）。

### 2. 導入先には配った物をコミットさせない（lockfile 方式）

npm が `package-lock.json` だけをコミットして `node_modules` をコミットしないのと同じ考え方。

| ファイル | 扱い |
|---|---|
| `.harness/manifest.json` | **コミットする**（lockfile にあたる。版と、入れた source のコミット `source_commit` を持つ） |
| seed（`docs/` の雛形、`.harness/checks.sh`） | コミットする（一度入れたらプロジェクトの持ち物） |
| `CLAUDE.md` | コミットする（managed だが、プロジェクトが書いた内容を残す特別扱い。gitignore するとその内容が消える） |
| `.claude/settings.json` | コミットする（manifest に載らないマージ方式で、プロジェクトの設定と同居する） |
| `AGENTS.md` の管理ブロック | 未確定（計画の未確定事項） |
| 上記以外の managed / generated（CLI、スクリプト、スキル、役割ファイル、`.githooks/`、`.codex/hooks.json` など） | **gitignore する** |

コマンドは役割で 2 つに分ける。

| コマンド | 役割 | npm で言うと | コミットするもの |
|---|---|---|---|
| `harness install`（新設） | manifest の `source_commit` の中身をそのまま入れる。manifest は変えない。clone 直後や、他の人が版を上げた後に回す | `npm ci` | なし |
| `harness update` | source の最新（または `--ref`）を入れ、manifest の `source_commit` を書き換える | `npm update` | manifest だけ |

どの版を入れたかは gitignore した手元のファイルに記録し、SessionStart と `doctor` が manifest と比べて、ずれていれば「`harness install` を回す」と案内する。

## 落選案と落選理由

- **検査の強化だけ**: すり抜けたときに配った数だけ消せない痕跡が残る。100 リポジトリに配った後では手遅れになる。
- **コミットしない形だけ**: 混入した版を配ってしまえば、各 PC の作業ツリーと、その間にエージェントが読んだ文脈には入る。形で分かるものは出口で止める方が安い。
- **禁止語リスト（機械ローカルでも）**: リスト自体が会社名やプロジェクト名の一覧になる。コミットしなくても、PC に「漏らしたくない名前の一覧」を作って持ち歩くことになる（2026-10-16 にユーザーが却下）。
- **clone 直後も `update` で済ませる**: `update` は `source_ref` が空だと source の既定ブランチの最新を入れる（`bin/harness` の `resolve_source`）。manifest にはコミットが無く、タグも無いので、固定した版を再現できない。「clone するたびに最新版になる」だけで lockfile にならない。
- **plugin / マーケットプレイスで配る**（DESIGN.md §10 決定 #8 で落選済み）: リポジトリに置く必要がある `docs/` の雛形や `checks.sh` を運べないこと、Claude 専用になることは変わらない。lockfile 方式は「CLI で配る」という #8 の方式のまま、コミットする範囲だけを変える。

## 影響・やり直す条件

- 決定 #8 の理由のうち「リポジトリに入っていることが前提」は、managed / generated については成り立たなくなる。clone した直後は `harness install` を 1 回回すまでハーネスの道具（スキル、検査のランナー、CLI、役割ファイル）が無い。同梱の CLI も gitignore されるので、clone 直後に使えるのは `self-install` した `harness` か curl だけになる。
- **source の履歴を作り直すと、固定したコミットが消えて `install` できなくなる。** そのときは黙って最新を入れず、止まって `update` を案内する。
- 版を上げたときにコミットされるのは manifest の 1 行（`source_commit`）だけになる。混入した版を配っても、導入先の履歴に残るのはコミットのハッシュだけ。
- managed ファイルの扱いが変わるので major（1.0.0）。
- **やり直す条件**: clone 直後の `install` 忘れでハーネスが効かない事故が繰り返し起き、SessionStart や `doctor` での案内で防げない場合は、コミットする範囲を見直す。

## 改訂の経緯（2026-10-16、実装前）

- 初版は機械ローカルの禁止語リストで固有名も止める案だった。リスト自体が固有名の一覧になるためユーザーが却下し、形で分かるものだけの検査に絞った。
- 初版は clone 直後に `harness update` を回す案だった。検算で `update` が最新版を入れてしまい版を固定できないと分かったので、`install` と `source_commit` を足した。
