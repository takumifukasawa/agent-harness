# 0013: ペイロードの混入を「検査で止める」と「導入先にコミットさせない」の二重で封じる

- 日付: 2026-10-16
- 状態: 採用（実装は [計画 payload-containment](../plans/active/payload-containment.md)）

## 背景

2026-10-16 の公開前の精査で、ペイロード（`harness/`）の 2 か所（`scripts/doctor.sh` と `scripts/seed-case.sh` のコメント）に、導入先の実プロジェクトの名前が入っていたことが分かった。この 2 つは managed なので、`update` を通して他の導入先にも配られ、**そこでコミットされている**（入ったのは 0.8.0 なので、0.8.0 以降に `init` / `update` した導入先すべてが対象）。このリポジトリ側は履歴を作り直して消せたが、導入先の履歴に入ったものはこちらからは消せない。

問題はミスの種類によって重さが違うこと。

| ミスの種類 | 導入先でコミットする（〜0.11） | 導入先でコミットしない |
|---|---|---|
| スクリプトのバグ | `update` で直る | `update` で直る |
| 固有情報の混入 | **配った数だけ他人の履歴に残り、消せない** | `update` で消え、履歴に残らない |

検査をいくら強くしても、すり抜けた 1 回が消せないことは変わらない。逆に、コミットさせない形だけだと、手元の検査が無いぶん混入そのものは減らない。

## 採用案

二重にする。

1. **検査で出口を止める。** 機械ローカルの禁止語リスト（会社名・プロジェクト名・ゲーム名など。**リスト自体が固有名の一覧になるのでコミットしない**）で、ペイロードを次の 3 か所で検査する。
   - このリポジトリの pre-commit（混入したコミットを作らせない）。ここではペイロードに限らず**全ファイルと `git config user.email`** を見る。今回公開されたものの大半は、配らない `docs/` と作者のメールアドレスだった
   - `init` / `update` で導入先へ書き込む直前（配る側の PC のリストで止める）
   - `upstream` で導入先から戻すとき（導入先の固有名が入ってくる、一番ありがちな経路）
2. **導入先には配った物をコミットさせない（lockfile 方式）。** npm が `package-lock.json` だけをコミットして `node_modules` をコミットしないのと同じ考え方。
   - コミットする: `.harness/manifest.json`（版と source の固定）、seed（`docs/`、`.harness/checks.sh`。一度入れたらプロジェクトの持ち物）、`CLAUDE.md`（managed だがプロジェクトが書いた内容を残す特別扱いなので、gitignore するとその内容が消える）、`.claude/settings.json`（マージ方式でプロジェクトの設定と同居する）
   - コミットしない: managed / generated（CLI、スクリプト、スキル、役割ファイル、`.githooks/` など）。gitignore し、clone ごとに `harness update` で入れる
   - `AGENTS.md` の管理ブロックの扱いは未確定（計画の未確定事項）

## 落選案と落選理由

- **検査の強化だけ**: すり抜けたときに配った数だけ消せない痕跡が残る。100 リポジトリに配った後では手遅れになる。
- **コミットしない形だけ**: 混入した版を配ってしまえば、各 PC の作業ツリーと、その間にエージェントが読んだ文脈には入る。出口で止める方が安い。
- **plugin / マーケットプレイスで配る**（DESIGN.md §10 決定 #8 で落選済み）: リポジトリに置く必要がある `docs/` の雛形や `checks.sh` を運べないこと、Claude 専用になることは変わらない。lockfile 方式は「CLI で配る」という #8 の方式のまま、コミットする範囲だけを変える。
- **禁止語リストをコミットする**: リスト自体が会社名やプロジェクト名の一覧になり、漏らしたくないものを公開することになる。

## 影響・やり直す条件

- 決定 #8 の理由のうち「リポジトリに入っていることが前提」は、managed / generated については成り立たなくなる。clone した直後は `harness update` を 1 回回すまでハーネスが効かない（`npm install` と同じ）。同梱の CLI も gitignore されるので、clone 直後に使えるのは `self-install` した `harness` か curl だけになる。
- 禁止語リストは機械ローカルなので、リストを持たない人が `update` したときは配布時の検査が効かない。そのときは lockfile 方式だけが守りになる。
- managed ファイルの扱いが変わるので major（1.0.0）。
- **やり直す条件**: clone 直後の `update` 忘れでハーネスが効かない事故が繰り返し起き、`doctor` や SessionStart での案内で防げない場合は、コミットする範囲を見直す。
