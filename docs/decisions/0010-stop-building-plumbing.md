# 0010 — ②配管（gc）の作り込みを打ち止めにして、①ワークフローに戻る

- 日付: 2026-09-23
- 状態: 採用

## 決めたこと

**`harness gc` の項目をこれ以上増やさない。** [handoff-writeback](../spec/handoff-writeback.md)（項目 12）を最後とし、以後は**実害を踏んでから**足す。

代わりに `DESIGN.md` §11 の **⬜3 dogfood（自分のプロジェクト 1 つで機能 1 つを §5 で通す）**に移る。

## なぜ

`DESIGN.md` は冒頭で ①**ワークフロー（主役）** と ②**配管（支える仕組み、最小限）** に分け、「②は最小限に留める」「①を優先」と明記している。SmartHR から取り入れたのは①（4 役割、1 セッション 1 タスク、状態 JSON、**プロダクトに対する**機械検査、合意の書き戻し、最後に 1 回のレビューと反証）であって、`gc` は②配管の一部で出典も別（OpenAI の doc-gardening）。

**実態は設計と逆だった。**

- **5 題材のうち 4 題材が②の配管**（cross-env / onboarding-polish / no-silent-failures / writeback-sensors）
- その間 **§11 の ⬜3 dogfood は ⬜ のまま**
- `gc` は 7 → 11 項目に増え、さらに 14 項目にしようとしていた

| | SmartHR の 12 項目 | うちの `gc` 11 項目 |
|---|---|---|
| 何を検査するか | **プロダクトのコード**（テスト実行、テスト 0 件で green を防ぐ、除外リストへの追記を塞ぐ） | **docs の管理状態**（索引、状態欄、鮮度、リンク） |
| 効果が出る先 | 作っているプロダクト | ハーネスの運用そのもの |

`gc` 自体は 0.55 秒・28 シナリオで動くものとしては健全で、問題は複雑さではなく**配分**。**項目を増やしても、それを検証できる場が今このリポジトリ 1 つしか無い。**実プロジェクトで使ってみないと、何が本当に効くかは分からない。§11 の ⬜3 が「確かめること」に挙げているのも、まさに「`checks.sh` に何を登録すると効くか」である。

## 落選案

- **rot-coverage の 4 タスク（A〜D）を全部やる。** カバレッジ表が埋まり「終わりの条件」が可視化されるが、`gc` は 14 項目になり、①の dogfood はさらに後回しになる。**表を作ること自体が②の作り込み**である
- **#18 も含めて全部捨てて即 dogfood へ。** 切り替えは最も早いが、「直す必要がある」と合意した実害のある穴を先送りすることになる（#18 は 2026-09-22 に再発を実測済み）
- **B・C を残す。** B（サブディレクトリの索引漏れ）の実物 3 件は 2026-09-22 に**手で直して数分で済んだ**。C（`DESIGN.md` の腐り）も同様。**手で済む頻度のものに検査を作るのは②の過剰投資**

## 再開の条件

`gc` の項目を再び増やすのは、**同じ腐りを 2 回踏んだとき**。1 回目は手で直して `docs/learnings.md` に記録する。
