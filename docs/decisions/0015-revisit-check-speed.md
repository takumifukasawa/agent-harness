# 0015: 検査の速度を見直す（決定 0008 の再浮上条件に当たった）

- 日付: 2026-11-25
- 状態: 採用（実施は計画 [check-speed-2](../plans/active/check-speed-2.md)）

## 背景

決定 0008 は「`check` が再び 60 秒を超えたら見直す」とした。2026-11-25 の実測でフルの `check` は **1727 秒**、pre-commit の `--fast` は **約 4.6 分**になった（内訳は計画の「背景」）。原因は、プロセス 1 回の起動が高い環境（`git` 1 回 12ms、待ちが中心）、他の `check` との同時実行、決定 0008 の後に足したシナリオ一式と、それに付いた `fast` の印。

決定 0008 が打ち切った理由は「残りの改善は 50 秒のうち 2〜4 秒で、壊してはいけない経路を触る取引になる」だった。プロセス 1 回の値段が数倍になり、全体が 29 分になった今、その比率の前提は成り立たない。

## 採用案

**検査を減らさず緩めず、回し方を変える。** 次の 5 つ（計画の T01〜T07）。

1. pre-commit の `fast` を数秒で終わる検査だけに戻し、重い `fast` を `check.sh` が言う
2. フルの検査を回す場面を決める（実装役は関係する検査、フルは統括の判定と push 前）
3. `check.sh` で検査を並列に回す（出力は検査ごとに分け、登録順に表示）
4. `tests/doctor.sh` を分割して並列に回す（並列にしても一番長い検査より短くならないため、3 とセット）
5. 同じリポジトリでの二重起動を防ぐ

`doctor` の呼び出しや使い捨てプロジェクトそのものを減らす（決定 0008 の (c)）のは、1〜5 の後に測ってまだ長いときだけ。

## 落選案と落選理由

- **このまま（決定 0008 を維持）**: 1 タスクでフルが数回走ると、検査待ちだけで 1〜2 時間になる。実装役の所要（6〜22 分）と比べて無視できる、という 0008 の前提が崩れた。
- **シナリオを削る・束ねる**: `AGENTS.md` の「検査を弱めない」に反する。
- **プロセスの起動を高くしている環境を変える**: この PC のセキュリティソフトの設定で、ハーネスからは変えられない。導入先にも同じ環境の PC があると考える。
- **並列化だけをやる**: `doctor scenarios`（900 秒）が残り、全体がそれより短くならない。

## やり直す条件

- 1〜5 の後もフルの `check` が 5 分を超える: `doctor` の呼び出し・使い捨てプロジェクトの削減（計画 T07）に進む。
- 並列実行で、落ちた検査の原因が読めなくなった、または並列のときだけ落ちる検査が出た: その検査を直列の印で外し、原因（共有する一時ファイルなど）を直す。

## 追補（2026-11-25、1.8.0）: 既定は差分、フルは push の前

- **採用**: `harness check` の既定を、`on` で指定したパスが変わった検査だけを回す形にした。全部回す `--full` は、push の関門が「push する先端で通った記録」を求める。エージェントが `--changed` のような指示を覚えている必要が無く、付け忘れても遅くなる側に倒れない。飛ばした検査も上流に乗る前に必ず回る。
- **落選**: `--changed` を足し、使う場面を指示に書く（エージェントが読み飛ばすと毎回フルになる。フルを回す保証も指示頼みになる）。既定を差分にして major（2.0.0）にする（`on` の無い検査は毎回回るので、導入先の挙動は `on` を書くまで変わらない。変わるのは push 前の `--full` だけで、managed ファイルの移動やマーカー形式の変更ではない）。
- **影響**: `on` の指定が狭すぎると、普段の check でその検査を飛ばす。push 前の `--full` で捕まるが、手戻りが遅れる。迷うパスは広めに書く。

## 追補（2026-11-25、1.9.0）: push 前のフルの検査は on を使うプロジェクトだけ

- **採用**: push の関門がフルの検査の記録を求めるのは、`.harness/checks.sh` に `on` を付けた検査があるときだけ。ユーザーが「push が遅くなるのは嫌。コミットで防げているなら push で遅くなる必要は無いのでは」と問い、push 前の `--full` が新しく捕まえるのは「完了時の check の回し忘れ」と「`on` が狭くて飛ばした検査」の 2 つだけだと整理した。`on` の無いプロジェクトでは後者が起きず、前者は管理ブロックの指示と統括の判定で防いでいる。
- **落選**: 全プロジェクトで必須（1.8.0。`on` の無いプロジェクトでは同じ検査を 2 回回すだけで、push が遅くなる）。全部やめる（`on` を使うプロジェクト、特にこのリポジトリでは、飛ばした検査が一度も回らずに上流に乗り、全導入先に配られる）。`on` の無い検査を既定で飛ばす（ハーネスには検査とパスの対応が分からず、導入先で検査がほぼ回らなくなる）。
- **影響**: 導入先を軽くするには、エージェントが `checks.sh` の重い検査に `on` を付ける（スキルの手順と 1.9.0 の CHANGELOG で案内）。

## 追補（2026-11-26、1.11.0）: タスクごとの検査は --since と related、フルは最終レビューの前

- **きっかけ**: GitHub issue #2。導入先の task-orchestrate の run で、タスクごとの `check` が 12〜25 分かかった。原因は 2 つ。(1) `on` はパスでしか絞れず、アプリのリポジトリではどのタスクも `src/` を触る。(2) 差分の起点が「push していない範囲」なので、push せずに何十タスクも進めると run 全体が差分になる。
- **採用**: `harness check --since <ref>` で差分の起点をタスクを始めたコミットにする。`checks.sh` の検査に `related "<コマンド>"` を書けば、`--since` のときだけ変わったファイルを渡して関係するテストを選ばせる（どれが関係するかはプロジェクトのツールが決める。ハーネスは import の関係を知らない）。task-orchestrate は `start_commit` を記録し、実装役と統括のタスクごとの判定を `--since` にする。フルは §3 の最終レビューの前に 1 回（落ちたら修正タスク）と、push の前（関門。今までどおり）。2026-11-26 にユーザーが合意。
- **1.8.0 の落選案（`--changed`）との違い**: あれは既定を軽くする手段を指示に頼る案で、付け忘れると毎回フルになり、フルを回す保証も指示頼みになるのが落選理由だった。今回は既定の挙動を変えない追加で、付け忘れても遅くなるだけ（安全側）。フルは §3 の手順と push の関門で必ず回る。
- **落選**: `fast` と並ぶ `light` の印で「関係するテストだけのコマンド」を別の検査として登録する（同じ検査を 2 行で管理することになり、片方だけ直す事故が起きる）。ハーネスが import の関係をたどってテストを選ぶ（言語ごとの知識が要り、依存は git と bash だけの規約に反する）。
- **影響**: import をたどらない影響（文言・CSS・設定ファイル）と e2e の件数の下限は、タスクごとの判定では見ない。最終レビューの前の `--full` で捕まるが、手戻りはタスク単位より遅れる。消した・名前を変えたファイルがあるタスクでは `related` を使わず本来のコマンドを回す。
- **やり直す条件**: 最終レビューの前の `--full` で落ちる検査が毎回のように出て、修正タスクが run の大半を占めるようなら、§2.5 の区切りでのフルを増やすか、`related` の対象を見直す。
