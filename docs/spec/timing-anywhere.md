# timing-anywhere — 計画を立てない小さな作業でも所要時間を記録できるようにする

状態: **合意済み（2026-09-28）**

## 目的

`harness task start/done` と `harness eta` を作った**直後の作業で、自分で使えなかった**。

2026-09-28 に負債 #19（`tests/eta.sh` の flaky）を返済したとき、「1 タスクで終わるから」と `.harness/state/` を作らなかった。`task-orchestrate` §5 の「1 セッションで終わる変更には使わない」に従った判断で、それ自体は正しい。**しかし記録も取れなくなった。**ユーザーに「あとどれくらい？」と聞かれて、また推測で答えることになった。

**記録を取るだけなら、計画も spec もタスク分解も要らない。**`harness task start <id>` を叩けるかどうかだけが問題で、いまはその前提に `.harness/state/stages.json` の存在がある（無ければ `exit 1`）。

## 受け入れ条件

### A. state が無くても記録できる

- A1. **`.harness/state/` が無い状態で `harness task start <id>` を叩いたら、記録を始められる。** 最小限の state を自動で作ってよい
- A2. **作ったことを黙らない。** 「`.harness/state/` が無かったので作った」と言う（`docs/spec/no-silent-failures.md` の原則）
- A3. **`tasks` 配列が空でも `timings` だけで記録できる。** 計画を立てない作業ではタスク一覧が無いのが正常な状態
- A4. **既存の挙動を変えることになるので、そのテストも直す。** いま `tests/task-timing.sh` の TT4 は「`.harness/state/` が無ければ黙って失敗せず案内して exit 1」を検証している。**これは「弱める」のではなく「仕様を変える」変更**なので、変更の理由をテストのコメントか report に残すこと。`stages.json` が壊れている・読めない場合は**引き続き失敗する**（そこは弱めない）

### B. `eta` が tasks の無い記録でも役に立つ

- B1. **`tasks` が空でも、`timings` に実績があれば「何分かかったか」を出す。** いまは `phase: no_tasks` で「不明」と言って終わる
- B2. **進捗（N/M）は出せないと正直に言う。** タスク一覧が無いので分母が無い。**数字を捏造しない**（既存 B3 の原則）
- B3. **実行中のもの（`done_at` が null）があれば、その経過時間を出す**
- B4. `--json` も同じ情報を持つ

### C. 使い方が統括に届く

- C1. **`task-orchestrate` に「計画を立てない小さな作業でも `harness task start/done` は使える」と書く。** 今回の失敗は「スキルが `task-orchestrate` の文脈でしか説明していない」ことが原因でもある
- C2. `harness` スキルのサブコマンド表にも同じ旨を足す

### D. 回帰

- D1. `tests/` に回帰シナリオを足す。A1〜A3、B1〜B3 それぞれ
- D2. **実装を壊すと実際に落ちること**を確認する

## 範囲外（やらないこと）

- **記録の自動化（hook）。** [task-timing の spec](task-timing.md) の C3 のとおり、叩き忘れが実際に困ってから
- **タスク一覧の推測。** `timings` の id からタスクを逆算したりしない
- **複数の題材にまたがる集計。** state は題材ごとに作り直される前提のまま

## 合意済みの決定（2026-09-28）

- **「2 回踏んだら仕組みにする」（[決定 0010](../decisions/0010-stop-building-plumbing.md)）の基準を、今回は 1 回で適用する。** ユーザーの判断。理由: **作った本人が翌日に使えなかった**という失敗の質が悪く、放置すると「記録を取る」習慣そのものが根づかない。踏んだ回数ではなく、**その機能の存在意義に直結するか**で見た
