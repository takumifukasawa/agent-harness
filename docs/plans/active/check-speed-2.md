# check-speed-2 — 検査の待ち時間を、回し方を変えて短くする

- 開始: 2026-11-25
- 状態: 進行中（T01 から着手）
- 関連: [決定 0015](../../decisions/0015-revisit-check-speed.md)（[決定 0008](../../decisions/0008-stop-optimizing-check-at-50s.md) の見直し）、[spec check-speed](../../spec/check-speed.md)（前回）

## 背景（なぜやるか）

2026-11-24 の 1.5.0 のコミットと push に約 10 分かかった。2026-11-25 に測り直すと（macOS / arm64、同じ機）:

| | 2026-09-21 | 2026-11-25 |
|---|---|---|
| フル `harness check` | 50s（18 件） | **1727s ≒ 29 分**（28 件） |
| `--fast`（pre-commit） | 1s（11 件） | **約 4.6 分**（gc 113s・eta 73s・push gate 36s・task timing 23s・source cache 23s など） |
| `doctor scenarios` | 34s | **900s**（全体の 52%） |
| `lockfile` / `update` / `codex` | — / 12s / — | 178s / 164s / 108s |

原因は 3 つ重なっている。

1. **プロセス 1 回の起動が高い**: `/usr/bin/true` 1 回 3.6ms、`git --version` 1 回 12ms、その間の CPU 使用率は 2〜6%（待っている）。エンドポイントのセキュリティソフトが起動のたびに検査を挟んでいるとみられる（CPU 86%）。テストは使い捨てのプロジェクトを作って `git` / `cp` を数千回起動するので、ここが効く。この PC の環境はハーネスからは変えられない
2. **同時に走る**: 他のプロジェクトの `check` が並行していた。同じリポジトリでフルと `--fast` が二重に走ったこともあった
3. **検査が増え、重いものに `fast` が付いた**: 決定 0008 の後に足したシナリオ一式が pre-commit に入り、1s → 約 4.6 分

## 目的（何ができれば完了か）

検査を減らしたり緩めたりせず（`AGENTS.md`）、回し方を変えて、(1) コミットのたびの待ちを数秒に、(2) フルの検査の壁時計時間を大きく縮め、(3) 1 タスクあたりにフルの検査が走る回数を減らす。(2) と (3) は配布物として全導入先に効かせる。

## 受け入れ条件

- [ ] `--fast`（pre-commit）がこのリポジトリで 10 秒以内。シナリオ一式はフルの検査で引き続き走る（件数は減らない）
- [ ] `--fast` で数秒を超える検査があると、`check.sh` がそれを言う（fast の印が重い検査に付いて、また遅くなるのを止める）
- [ ] 役割文・スキルが、いつフルの検査を回すかを決めている（実装役は関係する検査、フルは統括の判定と push 前）。最後に必ずフルが 1 回走る
- [ ] `check.sh` が検査を並列に回せる。出力は検査ごとに分け、表示は登録順。どの検査がなぜ落ちたかが今と同じく読める（決定 0008 の C2）。並列にできない検査を直列に残せる
- [ ] `tests/doctor.sh` を分けて並列に回せる。シナリオと判定は変えない
- [ ] 同じリポジトリで `check` が二重に走らない（後から来た方が待つか、知らせて止まる）
- [ ] 回帰テストを `.harness/checks.sh` に登録。macOS の bash 3.2 と Windows（Git Bash）で動く。`tests/lint-bash-compat.sh` が通る
- [ ] CHANGELOG に「プロジェクト側で必要な作業」（fast の付け方の見直し、並列にできない検査の印など）
