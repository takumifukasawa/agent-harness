# 0008: `harness check` の最適化は 50 秒で打ち切る（B の 3 件目はやらない）

- 日付: 2026-09-21
- 状態: 採用

## 背景

`docs/spec/check-speed.md` の B は「遅い検査を速くする」で、範囲を「A の実測後に確定する」としていた。2 件実施した結果:

| | フル `check` | 内訳 |
|---|---|---|
| A 実装時（2026-09-21） | 95s | `doctor scenarios` 58s + `update scenarios` 30s で 93% |
| B1（ハッシュのバッチ化） | 62s | 43s + 15s |
| B2（プロセス起動の削減） | **50s** | 34s + 12s |

**−47%。** ここで 3 件目に進むかを決める必要がある。spec の未確定事項に候補が 3 つ挙がっている: (a) `apply_plan` が no-op のときも 44 ファイルを毎回レンダリングする構造 (b) `plan()` の `basename` 16 回 (c) テストが作る使い捨てプロジェクトの複製・削除（4.5s）。

## 採用案

**打ち切る。** `check` の最適化としての B はここで完了とし、C（並列化）にも進まない。

根拠は B2 で取った実測にある。`update` 1 回 611ms の構成は**外部プロセス 125 個（≒225ms）と bash 自身の処理 386ms**で、候補 (a) (b) で現実に削れるのは `cp` 30 回 + `basename` 16 回 + `grep` 数回 ≒ **50 プロセス ≒ 90ms**。テスト全体で `update` は 26 回なので **2.4 秒**、フル `check` で **50s → 47.6s（−5%）**にしかならない。しかも (a) は `apply_plan`（`init` と `update` の中核で、ローカル変更の復元判断を担う）の構造に手を入れることになり、B1・B2 のような局所的な置き換えではない。**残り 2 秒台のために、いちばん壊してはいけない経路を触る取引になる。**

(c) は 4.5 秒あるが、`cp -a` と `rm -rf` の I/O そのものなので、削るにはシナリオが使う使い捨てプロジェクトの**数**を減らすしかない。これは実質シナリオの束ね直しで、`docs/spec/check-speed.md` の B2（検査を弱めて速くしない）に接触する判断が要る。50 秒という現状では、その判断を通してまで取りに行く価値がない。

**打ち切りの目安**: 当初 `docs/tech-debt.md` #6 が置いていた目標「20〜40 秒」は使わない。あれは Windows 機での見立てで、前提（`doctor` 1 回 ≒ 3 秒、`doctor.sh` 側の最適化が要る）が 2 つとも実測で覆っている（#6 の状態欄）。50 秒は「1 タスクにつき実装役 1〜2 回・統括 1 回・レビュアー数回」という使われ方に対し、実装役 1 体の所要（6〜22 分）と比べて無視できる比率に収まった。

## 落選案と落選理由

- **(a) `apply_plan` の no-op スキップまでやる**: 効果 2.4 秒に対し、`init` / `update` の復元判断という最も壊せない経路を触る。B1・B2 は「同じ判定をより少ないプロセスでやる」だったが、これは**判定そのものを飛ばす**変更で、性質が違う。将来 `update` 自体が体感で遅いという苦情が出たら、そのとき本番の所要（611ms）を理由に改めて検討する。
- **(b) `basename` 16 回を `${f##*/}` に置き換える**: 安全で 30ms 程度は取れるが、単体では `check` の 1 秒にも満たない。「ついでに直す」対象として、`plan()` を別の理由で触るときに一緒にやる。
- **(c) 使い捨てプロジェクトの数を減らす**: 4.5 秒あるが、B2（検査を弱めない）との境界判断が要る。数を減らすとシナリオ間の独立性が下がり、1 つの失敗が別のシナリオを巻き込む形に近づく。**テスト時間より、失敗したときに原因が読めることのほうが価値が高い**（C2 と同じ理由）。
- **C（並列化）に進む**: `check` 50 秒のうち 46 秒が 2 件（`doctor scenarios` / `update scenarios`）なので、18 件を並列化しても縮むのは残り 4 秒ぶん。支配的な 2 件を並列化するには、その中のシナリオを並列にする必要があり、出力が混線して「どの検査がなぜ落ちたか」が読めなくなる（C2 で不可としている）。**そもそも C は「B を終えてなお遅いときだけ検討する」（C1）で、その条件を満たしていない。**

## 再浮上する条件

- `check` の所要が再び 60 秒を超えたとき（検査が増えるのは健全なので、増えたぶんは受け入れる。そのうえで支配項目を A の出力で確認する）
- `harness init` / `update` の**本番の**所要が体感で問題になったとき（テスト時間ではなく、人が待つ時間として）
