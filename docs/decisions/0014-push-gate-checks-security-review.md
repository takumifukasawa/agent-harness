# 0014: push の前に 1 回だけレビューし、レビュー済みの印が無い push を hook で止める

- 日付: 2026-10-16
- 状態: 採用
- 改訂: 2026-10-16（同日、push 前）。初めは security-guidance プラグインの commit ごとのレビューの記録を見る形だったが、ユーザーの判断で「push の前に 1 回だけレビューし、問題があれば push していないコミットを書き換える」形に変えた。経緯は末尾

## 背景

Claude Code の security-guidance プラグインは、`git commit` のたびにコミットをレビューする（1 分前後かかる。指摘が無いときは何も知らせない）。2026-10-16 に、統括が commit と push を 1 つのコマンドで続けて実行したため、レビューの結果（指摘 2 件）が届いたのは push の後だった。指摘が秘密情報だったら手遅れになる。ユーザーの要望は「push はエージェントに頼みたい。ただし、レビューを通る前に push されないことを必須にしたい」「検査の量（時間と費用）はできるだけ減らしたい」。

1.1.0 で `permissions.ask: ["Bash(git push *)"]` を入れたが、実機（auto モード）では確認が出なかった。規則は `/permissions` に表示されており、コマンドも最も単純な `git push --dry-run` だった。公式 docs（permissions / permission-modes。2026-10-16 確認）は「auto モードでも ask は確認を出す」と書いており、実機と食い違う。一方、`deny` と PreToolUse hook の deny は同じセッションで確実に効いた。

## 採用案

1. **レビューは push 1 回につき 1 回。** commit ごとにはしない。push を頼まれたら、push していない範囲（`git log --branches --not --remotes`）をまとめてセキュリティの観点でレビューする。プラグインの commit ごとのレビューは、ユーザーの PC の設定（`~/.claude/settings.json` の `env.ENABLE_COMMIT_REVIEW=0`）で止める。
2. **問題なしなら印を付けて push する。** `bash .harness/scripts/push-gate.sh --stamp` が、push していないコミットを持つブランチ・タグの先端を `.git/harness-push-reviewed`（git の中。コミットされない）に記録する。
3. **問題があれば直し、push していないコミットを書き換えてからレビューし直す。** 上流に乗ったものは書き換えないので force push は要らない。`AGENTS.md` の「やらないこと」を「push 済みの履歴の書き換え」に改め、push していないコミットの書き換えは指示なしでよいとした。
4. **Claude Code の PreToolUse hook（`harness/adapters/claude/push-gate.sh`）が、印の無い push を止める。** push していないコミットを持つ先端がすべて印に載っていれば通す。先端が 1 つでも変われば（コミットを足した、書き換えた）印は効かなくなる。

hook が止めるもの（判定できない形は止める側に倒す。止めても人は `! git push` で通せる）:

| 形 | 理由 |
|---|---|
| 印の無い先端がある push | レビューしていない |
| commit / merge / rebase / pull などと push が同じコマンド | hook は実行前に走るので、そのコマンドで作られるコミットを印と照らせない |
| 展開（`$( )` など）・`eval`・`xargs`・`sh -c`・`--git-dir`・`GIT_DIR=` を通した push、シェルを通す git の alias | 何がどこへ push されるかを実行前に決められない |

push 先は `cd` / `pushd` / `git -C` を追って決める。HEAD だけでなく、ローカルのすべてのブランチとタグのうち push していないコミットを見る（`git push origin <別のブランチ>` や `--all` で確かめていないものが出ていかないように）。すべてが `--dry-run` の push と、push していないコミットが無い push は通す。ヒアドキュメントの中の文字はコマンドとして見ない。

## 落選案と落選理由

- **`permissions.ask` で push のたびに人が確認する（1.1.0）**: 実機で確認が出なかった。仮に出ても、人が「レビューが済んだか」を自分で調べる必要があり、関門としては弱い。
- **エージェントの push を `deny` で禁止し、人が `! git push` で打つ**: 確実だが、ユーザーは push をエージェントに頼みたい（2026-10-16 にユーザーが却下）。
- **プラグインの commit ごとのレビューの記録（`.git/sg-reviewed-shas`）を hook が見る**（この決定の初版）: レビューが commit の数だけ走り、時間と費用がかかる（commit 1 回 0.2〜1.6 ドルの見積もり）。指摘のあったコミットが記録に残り続け、直した後も関門が止め続ける。プラグインの記録の書式と、レビュー対象の判定（拡張子の許可リスト）に依存する。ユーザーが「検査の量を減らしたい」として却下した。
- **プラグインのログ（`~/.claude/security/log.txt`）から結果を読む**: 結果の行にコミットの sha が付いておらず、コミットごとの結果を確実に引けない。

## 影響・やり直す条件

- 印はエージェントでも書ける。この関門は「レビュー前にうっかり push する」ことを止めるもので、悪意のあるエージェントを止める境界ではない（Claude Code の docs も deny / ask を境界ではないと書く）。レビューを飛ばして印だけ付けることは、`AGENTS.md` の規律で止める。
- push のたびに 1 回レビューの待ちが入る（push していない範囲の大きさで 1〜数分）。
- Claude Code 専用。Codex には同等の関門が無い（Codex の deny hook は破壊的な操作だけを止める）。
- **判定できない push の経路**: push を中で呼ぶスクリプトや `make` / `npm run release`、`push.recurseSubmodules` によるサブモジュールの push、サブシェルの中の `cd`（`(cd x); git push` は x を見てしまう）。hook が timeout（10 秒）を超えると Claude Code は止めないので素通りになる（未 push の判定は `rev-list` 1 回にして軽くしてある）。
- 「止めすぎ」の側に倒しているので、コミットを作る操作と push を同じコマンドに書く、展開を使う、などの書き方は止まる。分けて書けば通る。
- **やり直す条件**: `permissions.ask` が実機で確認を出すようになったら、人の確認を足すかを考える。印を付ける前のレビューが形だけになっている（指摘が一度も出ない、範囲を読んでいない）と分かったら、レビューの手順を機械で残す形（レビューの結果のファイルを印に紐づける）を考える。

## 改訂の経緯（2026-10-16、push 前）

- 初版は、プラグインの commit ごとのレビューの記録を hook が見る形だった。それを入れたコミット自体にプラグインが 5 件の指摘を出し（HEAD しか見ていない、dry-run の判定がコマンド全体で 1 つ、`cd` / `-C` で別のリポジトリを見る、展開や alias を見逃す、記録が無いと素通りする）、関門が自分の push を止めた。
- ユーザーが「検査の量を減らしたい。push 前に push していない分をまとめて検査し、問題があれば push していない過去のコミットを書き換える方が正しいのでは」と提案し、それを採った。指摘のうち 4 件（別ブランチ、dry-run の混在、別リポジトリ、展開・alias）への対策は新しい hook にも入れた。5 件目（記録の偽造・不在）は、印もエージェントが書けるので同じ限界を持つ。上の「影響」に書いた。
