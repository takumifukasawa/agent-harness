# handoff-writeback — 計画を進めたのに handoff を放置していないか

状態: **合意済み（2026-09-23）**。[tech-debt #18](../tech-debt.md) の解消。**1 タスクで終わる規模。**

## 目的

`harness gc` は docs の腐りを 11 項目で検知しているが、**実際に一番よく踏む漏れ——統括が計画を進めたのに `docs/handoff.md` を更新しないままセッションを終える——だけが捕まらない**。

2026-09-22 の writeback-sensors で、まさにこれが再発した。**その題材自身が対象としていた漏れなのに、新設した sensor のどちらにも引っかからなかった**（2 体のレビュアーが独立に報告し、実測で確認）。原因は**頻度で見ていたこと**:

> `gc --commits` の既定値 10 は実測（`handoff` 更新間隔ごとの非 docs コミット数の**中央値 2、5 件以下が 30 区間中 26**）に基づく。つまり**発火するのは 30 回に 4 回程度の例外だけ**で、日常的な漏れは設計上すべて閾値の下に隠れる。閾値を 5 に下げる案は「通常のセッションで警告が出すぎる」として落選済みで、**その理由は今も正しい**。

そこで**頻度ではなく状態の矛盾**として見る。`gc` の項目 10（plan ↔ タスク表）と 11（spec ↔ plan）が確実に効いているのと同じ方式。

## 受け入れ条件

- A1. **`docs/plans/active/*.md` を最後に更新したコミットより後に `docs/handoff.md` が更新されていなければ報告する**
- A2. **日数やコミット数の閾値に依存しない。** 同じ日・1 コミットの漏れでも捕まること
- A3. `docs/plans/active/` が空なら何も言わない
- A4. 計画と handoff が**同じコミット**で更新された場合は報告しない
- A5. 回帰シナリオが `tests/gc.sh` にあり、実装を壊すと落ちる
- A6. `gc` が 1 秒を超えない（現状 0.55 秒。[#17](../tech-debt.md) のとおり docs 全体スキャンは既に重くなりかけている）

## 範囲外（やらないこと）

- **handoff の内容が正しいかの判定。** 見るのは「更新されているか」だけ。中身の正しさは人間とレビューの領域
- **統括の作業そのものの機械化**（書き戻しは統括の仕事。検査は「漏れを教える」までが範囲）
- **`gc` の項目をこれ以上増やすこと。** [決定 0010](../decisions/0010-stop-building-plumbing.md) のとおり、②配管の作り込みはここで打ち止めにして①ワークフローに戻る

## 合意済みの決定（2026-09-23）

- **比較対象は `state` ではなく計画。** ユーザーとの当初合意は「`.harness/state/progress.json` の `phase` と handoff の突き合わせ」だったが、実現方法を詰めて変えた。理由は 2 つ — (1) `.harness/state/` は **gitignore なので git 履歴が無く、コミットの前後関係で判定できない**。日付比較に落ちると、A2 で避けたい「同日の漏れを取り逃す」失敗を繰り返す (2) **実際に踏んだケースでは計画は正しく更新されていて handoff だけが古かった**ので、比較対象は計画が正しい。**目的（頻度ではなく状態の矛盾を見る）は変えていない**
- **B・C・D は落選。** 起票時は 4 つの受け入れ条件（A: これ / B: サブディレクトリの索引漏れ / C: `DESIGN.md` の腐り / D: カバレッジ表を `docs/architecture.md` に置く）で分解していたが、**②配管に偏りすぎているという指摘**を受けて A だけに絞った（[決定 0010](../decisions/0010-stop-building-plumbing.md)）。B と C の実物はこの題材の中で**手で直す**（実際、B の実物 3 件は 2026-09-22 に手で直して済んでいる）
