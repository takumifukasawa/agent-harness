# 0007: フックが実行不可なら doctor は FAIL にする（WARN ではない）

- 日付: 2026-09-20
- 状態: 採用

## 背景

T02 で、`.githooks/pre-commit` が git index 上で mode 100644 だったために **clone したツリーでは pre-commit が一度も走っていなかった**ことが分かった（git は `hint: ... not set as executable` を 1 行出して無視する）。`doctor` の B6 は `-f`（存在）しか見ていなかったので、その状態で `OK git hooks` と報告していた。**このリポジトリ自身が、検査の門番が不在のまま数セッション進んでいた。**

T02 は index を 100755 にし、B6 が実行可否（`-x`）まで見るように直した。ただし**重大度は WARN に据え置いた**。理由は「FAIL にすると、ハーネスを更新した既存プロジェクトの `harness check`（決定 0005 で入れた `doctor: FAIL 0`）が突然赤くなる」ため。

ここで方針判断が要る: 気づかせることを優先するか、既存プロジェクトを赤くしないことを優先するか。

## 採用案

**FAIL に上げる。**

「フックが実行不可」は**検査の門番が不在**という状態であって、劣化ではない。ハーネスは「`check` が通ることが完了の客観条件」という前提で組まれており（`AGENTS.md`）、その前提を守らせる装置が黙って無効になっているなら、それは FAIL 相当である。

WARN に据え置くと、`doctor` の総括行に `WARN=1` が出るだけで `check` は緑のままになる。**今回この穴を見逃したのと同じ見落とし方**を、既存プロジェクトでも再現することになる。

既存プロジェクトが一度赤くなるのは意図した動作とする。赤は「壊した」ではなく「もともと壊れていたものを可視化した」であり、`CHANGELOG.md` に修復手順（`chmod +x .githooks/pre-commit && git update-index --chmod=+x .githooks/pre-commit`）を書いてあるので、エラー文から手順に辿り着ける（`AGENTS.md` の「検査のエラー文に修復手順が書かれていれば、それに従う」）。

**配布 seed（`harness/checks.seed.sh`）に実行ビット専用の検査は足さない。** 決定 0005 で seed の `checks.sh` には既に `doctor: FAIL 0` が入っているので、B6 を FAIL にすれば seed 経由で自動的に効く。検査を二重に持つと、直す場所が 2 つになる。

**Windows で偽の FAIL を出さないこと**が前提条件。判定は T02 が入れた形を保つ: index の mode は常に見る、作業ツリーの `-x` は `core.filemode != false` のときだけ見る。

## 落選案と落選理由

- **WARN 据え置き（T02 の判断のまま）**: 既存プロジェクトを赤くしないが、`check` が緑のままなので**気づかない経路が残る**。今回の見落としをそのまま制度化することになる。
- **WARN のまま + seed の `checks.seed.sh` にも実行ビット検査を独立して足す**: 重大度の問題を検査の数で埋め合わせる形になる。`init` 直後はフックが未追跡で index を見る検査が素通りするので、効き始めるのは最初のコミット後であり、穴が残る。検査が 2 箇所に散るぶん保守も増える。

## 影響・やり直す条件

- `harness update` で 0.6.0 以降を取り込んだ既存プロジェクトは、`.githooks/pre-commit` の index mode が 100644 のままなら `doctor` が FAIL 1 になり、`check` の `doctor: FAIL 0` が落ちる。**これは意図した動作。** 修復手順は `CHANGELOG.md`。
- やり直す条件: この FAIL が**直しようのない環境**（フックの実行ビットを立てられないファイルシステム、CI の read-only チェックアウトなど）で出ると分かったら、その環境を検出して WARN に落とす条件を足す。重大度そのものを WARN へ戻すのではなく、判定条件を精緻にする方向で直す。
