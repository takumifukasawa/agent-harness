# 0005: seed の `checks.sh` に `doctor: FAIL 0` を最初から入れる

- 日付: 2026-09-18
- 状態: 採用

## 背景

`harness init` が配る `.harness/checks.sh`（seed）には、実質 1 件（`docs/README.md` の存在確認）しか検査が無い。残りはコメントアウトされた例だけで、プロジェクトが自分で書くまで **`harness check` はほぼ無条件に pass する**。

これは `AGENTS.md`（`task-orchestrate` §1.7）が自分で警告している状態そのもの:

> seed 直後の `checks.sh` は docs の存在確認 1 件しか無い。**このままだと検査は常に pass し、完了判定が空洞化する。**

統括は「完了判定は検査・git・状態の 3 点で決める」という規律で動くので、検査が空洞だと**判定の 1 本が最初から機能しない**。しかもそれに気づくのは、実装役が「できました」と言ったものを検証できないと分かった後になる。

v0.4.0 では、このリポジトリ自身の `.harness/checks.sh` にだけ `doctor: FAIL 0` を足した。効果があったので、新規プロジェクトにも最初から配るかを決める。

## 採用案

**seed の `checks.sh` に `check "doctor: FAIL 0" ...` を最初から入れる。**

```sh
check "doctor: FAIL 0" "bash .harness/bin/harness doctor || { echo 'doctor が FAIL を報告した。上の FAIL 行の「→」に従って直す。'; exit 1; }"
```

理由:

- **言語やスタックに依存しない唯一の検査**。`doctor` が見るのはプロジェクトのコードではなく**ハーネスの導入状態そのもの**（manifest、ファイルの存在、改行、git hooks、`AGENTS.md` のマーカー、アダプタ）なので、どのプロジェクトでも意味を持つ。他の検査（lint / test / 型）は書けるものが無いと配れない。
- **init 直後は必ず通る**。`tests/doctor.sh` の D1 が「init 直後の doctor は FAIL 0 / exit 0」を保証しているので、導入した瞬間に赤くなることはない。
- **費用が小さい**。実測 4.7 秒（`real 4.685s`）。`fast` は付けないので pre-commit（`harness check --fast`）は従来どおり即座に終わる。
- **空洞化に最初の 1 本で歯止めをかける**。`harness check` が「本当に何かを見ている」状態で始まるので、プロジェクトが 2 件目を足す動機にもなる。

## 落選案と落選理由

- **入れない（seed は最小限に保つ）**: seed は「プロジェクトが書き換える前提の雛形」なので、中身を増やすと押し付けになる、という考え方。落選理由は、これが**プロジェクト固有の判断を含まない**検査だから。lint やテストと違って「このプロジェクトではこうする」という余地が無く、押し付けにならない。空洞のまま配るコストのほうが大きい。
- **`fast` を付けて pre-commit でも走らせる**: 4.7 秒はコミットのたびに払うには重い。`--fast` は「数秒で終わるものだけ」と seed のコメント自身が定めている。落選。
- **`doctor` を `harness check` の中に直接組み込む（`checks.sh` を介さない）**: プロジェクトが外せなくなる。検査は `checks.sh` で一覧でき、要らなければ消せる、という構造を壊すので落選。消す判断をプロジェクトに残す。

## 影響・やり直す条件

- **既存プロジェクトには自動では入らない。** `checks.sh` は seed なので `harness update` は触らない（触ったらプロジェクトが書いた検査が消える）。取り込みたい既存プロジェクトは、上の 1 行を自分の `.harness/checks.sh` に足す。`CHANGELOG` の「プロジェクト側で必要な作業」に書く。
- **版を上げる必要は無い。** 新規プロジェクトは `harness init` が clone した時点の seed を受け取るので、版番号ではなくブランチの内容で決まる。managed / generated（`harness update` が配るもの）を変えていないため、既存プロジェクトに通知すべき変更も無い。
- **やり直す条件**: `doctor` が「プロジェクト側ではどうにもできない FAIL」を出すようになったら（例: 環境依存で必ず落ちる項目が増えた）、この検査は邪魔になる。そのときは seed から外すか、`doctor` 側を直す。現状の `doctor` は FAIL を「ハーネスの導入状態が壊れている」に限っており、直し方も各行に付いている（決定 0003）。
