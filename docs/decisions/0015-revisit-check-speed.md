# 0015: 検査の速度を見直す（決定 0008 の再浮上条件に当たった）

- 日付: 2026-11-25
- 状態: 採用（実施は計画 [check-speed-2](../plans/active/check-speed-2.md)）

## 背景

決定 0008 は「`check` が再び 60 秒を超えたら見直す」とした。2026-11-25 の実測でフルの `check` は **1727 秒**、pre-commit の `--fast` は **約 4.6 分**になった（内訳は計画の「背景」）。原因は、プロセス 1 回の起動が高い環境（`git` 1 回 12ms、待ちが中心）、他の `check` との同時実行、決定 0008 の後に足したシナリオ一式と、それに付いた `fast` の印。

決定 0008 が打ち切った理由は「残りの改善は 50 秒のうち 2〜4 秒で、壊してはいけない経路を触る取引になる」だった。プロセス 1 回の値段が数倍になり、全体が 29 分になった今、その比率の前提は成り立たない。

## 採用案

**検査を減らさず緩めず、回し方を変える。** 次の 5 つ（計画の T01〜T07）。

1. pre-commit の `fast` を数秒で終わる検査だけに戻し、重い `fast` を `check.sh` が言う
2. フルの検査を回す場面を決める（実装役は関係する検査、フルは統括の判定と push 前）
3. `check.sh` で検査を並列に回す（出力は検査ごとに分け、登録順に表示）
4. `tests/doctor.sh` を分割して並列に回す（並列にしても一番長い検査より短くならないため、3 とセット）
5. 同じリポジトリでの二重起動を防ぐ

`doctor` の呼び出しや使い捨てプロジェクトそのものを減らす（決定 0008 の (c)）のは、1〜5 の後に測ってまだ長いときだけ。

## 落選案と落選理由

- **このまま（決定 0008 を維持）**: 1 タスクでフルが数回走ると、検査待ちだけで 1〜2 時間になる。実装役の所要（6〜22 分）と比べて無視できる、という 0008 の前提が崩れた。
- **シナリオを削る・束ねる**: `AGENTS.md` の「検査を弱めない」に反する。
- **プロセスの起動を高くしている環境を変える**: この PC のセキュリティソフトの設定で、ハーネスからは変えられない。導入先にも同じ環境の PC があると考える。
- **並列化だけをやる**: `doctor scenarios`（900 秒）が残り、全体がそれより短くならない。

## やり直す条件

- 1〜5 の後もフルの `check` が 5 分を超える: `doctor` の呼び出し・使い捨てプロジェクトの削減（計画 T07）に進む。
- 並列実行で、落ちた検査の原因が読めなくなった、または並列のときだけ落ちる検査が出た: その検査を直列の印で外し、原因（共有する一時ファイルなど）を直す。
