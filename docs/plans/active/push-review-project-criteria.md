# push-review-project-criteria — push 前のレビューに、プロジェクト固有の観点を足せるようにする

- 開始: 2026-11-13
- 状態: 計画中（ブリーフ。導入先のセッションから起票。着手はユーザーの判断待ち）
- 関連: [決定 0014](../../decisions/0014-push-gate-checks-security-review.md)（push の関門）、[決定 0013](../../decisions/0013-contain-payload-leaks.md)（固有名は機械では止めない）

## 背景（なぜやるか）

ある導入先が、「参考にしたアプリ・ゲーム・資料などの固有名詞をリポジトリに書かない」という規約を持った（技術的な依存先や連携先の名前は書いてよい）。これを公開される履歴に残さないよう止めたい。

最初は「書かない言葉の一覧（PC ごと・gitignore）を leak-audit にかけ、commit-msg / pre-push でも止める」案を考えたが、**一覧に載っていない名前は素通りする**。新しい参考元が出るたびに一覧へ足し続けることになり、結局すべてを列挙しておく方式（ホワイトリストと同じ性質）の難しさに戻る。決定 0013 が「固有名は機械では止めない」とした理由と同じ。

一方、このハーネスには**push の関門**（決定 0014）がすでにある。push する前に未 push の範囲をまとめてレビューし、レビュー済みの印が無い push を Claude Code の PreToolUse hook が止める。レビューの観点は今はセキュリティだけ。ここに**プロジェクトごとのレビュー観点**を足せれば、固有名詞のように「一覧ではなく判断で見るしかないもの」を、push 前に、判断で止められる。

- 初めて出てきた名前でも、レビュアーが文脈で「参考元の固有名詞か」を判断できる。許してよいもの（技術的な依存先など）も、規約の文面から判断できる。
- レビューの対象は未 push の範囲なので、中身だけでなく**コミットメッセージ**も含む。push 前なら書き換えて直せる（決定 0014 の流れのまま）。
- 印が無ければ push できないので、止まる側に倒れる。

決定 0014 の「やり直す条件」にある「印を付ける前のレビューが形だけになっていると分かったら、レビューの結果のファイルを印に紐づける」も、この題材で一緒に扱う。

## 目的（何ができれば完了か）

導入先が、push 前のレビューで必ず見る観点を自分のリポジトリに書いておけ、レビューはセキュリティに加えてその観点でも未 push の範囲（中身・コミットメッセージ・ブランチ名）を見る。何を見て問題なしとしたかの記録が印と一緒に残る。観点を書いていない導入先は今と変わらない。

## 受け入れ条件（検査で確認できる形に）

- [ ] 導入先が、プロジェクト固有のレビュー観点を書くファイルを持てる（seed。コミットされる。置き場は未確定事項 1）。`init` は空の雛形を置くか、置かない
- [ ] push 前のレビューの手順（どこに書いてあるかは未確定事項 2）が、そのファイルがあれば必ず読み、各観点で未 push の範囲を見ることを求める。対象は中身・コミットメッセージ・ブランチ名
- [ ] 印（`push-gate.sh --stamp`）を付けるとき、レビューの記録（見た範囲、適用した観点、結果）を残す。記録の無い印は効かない、などの形で印に紐づける（形式は未確定事項 3）
- [ ] 観点のファイルが無い導入先では、レビューの手順も hook の挙動も今と同じ（回帰）
- [ ] 観点の文面そのものは公開されうる（seed でコミットされる）ので、観点には「参考元の名前」を例として書かず、一般的な言い方で書くよう雛形・手順で案内する
- [ ] 回帰テスト（`tests/push-gate.sh` にシナリオ追加など）を `.harness/checks.sh` に登録する
- [ ] Windows（Git Bash）と macOS（bash 3.2）で動く。`tests/lint-bash-compat.sh` が通る
- [ ] CHANGELOG に「プロジェクト側で必要な作業」（観点のファイルの書き方）を書く

## 決定ログ

- 2026-11-13: 起票。当初の「leak-audit の commit-msg / pre-push を配る」案は、一覧に載らない名前を止められない（列挙の問題）ので主役にしない。主役は push 前のレビューの観点。一覧の検査は導入先の seed に任意の補助として残す。
- 2026-11-26: GitHub issue #1（機械識別子＝端末の UDID / CoreDevice の ID・署名のチーム ID・端末名・LAN の IP がコミットに入った）を受け、既定の観点の候補に「機械識別子」を足す。1.10.0 では文章のルールだけ入れた（決定 0013 の追補）。

## 未確定事項（人間の判断待ち）

1. **観点のファイルの置き場**: `docs/rules/push-review.md` のように docs に置くか、`.harness/push-review.md` のように `.harness/` に置くか。
2. **レビューの手順の置き場**: 今は hook のコメントと README にあるだけ。レビューを確実に同じ手順で回すため、スキル（例: `push-review`）にするか。
3. **記録と印の紐づけ方**: 記録のファイル（`.git/` の中。コミットされない）に、見た範囲（先端の sha）と観点ごとの結果を書き、`--stamp` がそれを要求する、など。記録もエージェントが書けるので、境界ではなく「形だけのレビュー」を減らす仕組みである点は 0014 と同じ。
4. **Codex での扱い**: push の関門は Claude Code 専用（0014）。Codex では観点を手順として読ませるだけにするか。
