# task-timing — 「あとどれくらいで終わるか」を推測ではなく記録から答える

状態: **合意済み（2026-09-25）**。未確定 3 件を確認し、`/double-check` で前提を検証して 3 件補強した。

## 目的

**統括は「あとどれくらい？」に毎回その場の推測で答えている。** 2026-09-23 の 1 セッションで 3 回聞かれ、3 回とも次のような間接的なシグナルから見積もった:

- そのセッション内で観測した他タスクの所要時間（完了通知に出るが**どこにも残らない**）
- コミットの有無、report ファイルの有無、エージェントの出力ファイルの更新時刻

**セッションをまたぐと、この推測の土台が消える。** 過去に「実装役 約 12 分」と計画へ手書きした例はあるが（`docs/plans/completed/harness-doctor.md`）、書く人と書かない人がいて統計にならない。

**git のコミット時刻から取れないかを先に検証した（2026-09-25）。取れない。** タスクのコミット間隔には**統括の作業が混ざる**:

| | git のコミット間隔 | 実装役の実測 | 差 |
|---|---|---|---|
| T03 | 17 分 | 10.5 分 | 6.5 分 |
| **T04** | **39 分** | **15.9 分** | **23 分** |
| T05 | 13 分 | 10.3 分 | 2.7 分 |
| T06 | 10 分 | 6.0 分 | 4.0 分 |

T04 の差 23 分が決定的で、**この間に統括が最終レビュー 4 体を起こして待っていた**。検査（93 秒）・書き戻し・コミットも毎回挟まる。**だから記録が要る**（この検証を書き残すのは、次に読む人が同じ検討をやり直さないため）。

記録が残れば、二次的な効果もある: **タスク分解の粒度を実績で判断できる**。いまは「1 タスク = 1 セッションで終わる量」を感覚で決めており、2026-09-23 の実測（6〜24 分）も会話の中にしか無い。

## 受け入れ条件

### A. 記録する

- A1. `.harness/state/stages.json` の各タスクに**開始時刻と終了時刻**を持たせられる
- A2. 記録は **CLI で行う**（例: `harness task start T01` / `harness task done T01`）。**特定のエージェントの機能に依存しない**（`DESIGN.md` §2 原則 6）
- A3. **時刻が無いタスクがあっても壊れない。** 既存プロジェクトの `stages.json` には無いフィールドなので、欠けている場合は「不明」として扱い、他の計算を止めない
- A4. 時刻の形式は**そのまま比較・差分計算ができるもの**にする（ISO 8601 / UTC）。ロケールや `date` の実装差（GNU / BSD）に依存しない

### B. 出す

- B1. **`harness eta`** が、進行中の題材について次を出す: 完了済みタスク数 / 全体数、経過時間、**残りの推定**、**推定完了時刻**
- B1b. **所要時間だけでなく時刻も出す**（2026-09-25 追加）。「あと 30 分」より「19:15 頃」の方が予定を立てやすい場面がある。**記録は UTC（A4）だが、表示はローカルタイム**（読むのは人間）。幅で推定するので時刻も幅になる（例: `19:05〜19:25`）
- B2. **推定は幅で出す。** 2026-09-23 の実測は 6〜24 分とばらついており、長かったのは外部ネットワークを使う工程（`browser-check`）を含むタスクだった。**単純な平均は外す**
- B3. **実績が足りないときは「不明」と言う。** 1 件も記録が無い、または進行中の題材が無い場合に、数字を捏造しない（`docs/roles/` の「根拠のない反証は認めない」と同じ姿勢）
- B4. **`--json` で機械可読な出力も出せる。** 外部の UI（Orca 等）がどの形を読めるか未確認なので、テキストと JSON の両方を用意して潰しを効かせる
- B5. `gc` と同じく**速い**こと（`stages.json` を読むだけなので、実測で 1 秒を切る）
- B6. **記録が欠けているタスクを出力で指摘する。** A2 は「統括が CLI を叩く」方式なので、**叩き忘れれば記録は残らない**。これは `writeback-sensors` が扱った「統括を縛るものが文章しかない」と同じ構図で、実際に統括は同じ日に `docs/handoff.md` の更新を忘れている（[tech-debt #18](../tech-debt.md) の発端）。**`gc` に検査を足すのは [決定 0010](../decisions/0010-stop-building-plumbing.md) に反する**ので、`harness eta` の出力自身が「T03 は時刻が記録されていない」と言う形で気づけるようにする

### C. 測る単位

- C1. **単位は「統括が `start` / `done` で囲んだもの」**。タスクもレビューも同じ仕組みで記録する（`harness task start T01` / `harness task start review`）。レビューを特別扱いしない
- C2. **`harness eta` はタスクとレビューを分けて足す。** レビューは題材ごとに 1 回で、観点数を増やしても並列なのでさほど伸びない（実測: 4 観点 17 分 / 2 観点 10 分 / 1 観点 10 分）。**「残数 × 幅」ではなく固定的な幅**として扱う
- C3. **hook による自動化は今回やらない**（2026-09-25 に合意）。まず CLI を作り、叩き忘れが実際に困ってから hook を足す（[決定 0010](../decisions/0010-stop-building-plumbing.md) の「実害を踏んでから」と同じ基準）。**hook が無くても成立する設計にする**（`DESIGN.md` §2 原則 6）

### D. 回帰

- D1. `tests/` に回帰シナリオがあり、実装を壊すと落ちる。`.harness/checks.sh` に登録する
- D2. 見るのは少なくとも: 記録できること / 時刻が無いタスクで壊れないこと / 実績が無いとき「不明」と言うこと / `--json` が妥当な JSON を出すこと

## 範囲外（やらないこと）

- **Orca 連携そのもの。** 何を読めるか未確認。テキストと JSON を出すところまでが範囲
- **実装役の「中」の進捗**（何割終わったか）。エージェントの内部状態は覗けない
- **履歴を溜めてタスクの性質ごとに見積もること。** 「テスト追加なら平均 8 分」のような分類は、データが溜まってから考える（今は 1 セッションぶんしか無い）
- **完了時刻からの締切逆算や通知。** 出すのは現在地と幅のある推定まで
- **中断の検出・除外。** セッションをまたぐ空白（実例: 2026-09-22 14:14 のコミットから翌日 11:05 まで 21 時間）は**イレギュラーとして考慮しない**（2026-09-25 合意）。出すのは素直な経過時間で、中断が混ざればその分ずれる
- **hook による自動記録**（C3 のとおり後回し）

## 合意済みの決定（2026-09-25）

- **hook は今回やらず、CLI だけ作る。** 落選: hook も同時に実装（Claude と Codex でイベント名も設定ファイルも違い、両方の実機確認が要る。タスクが 5〜6 本に増える）、hook だけで CLI を作らない（設定していない環境で何も記録されず、原則 6 に反する）
- **推定は幅（最小〜最大）で出す。** 実測が 6〜24 分と 4 倍のばらつきがあり、長かったのは外部ネットワークを使う工程を含むタスクだった。落選: 平均 × 残数の 1 点（ばらつきの大きい実態で大きく外す）、推定せず経過だけ出す（「あとどれくらい？」への答えにならない）
- **タスクとレビューの両方を測る。** ユーザーが知りたいのは「題材がいつ終わるか」なので、レビューを測らないと答えられない。ただし統計の性質が違うので分けて扱う（C2）
- **中断は考慮しない。** イレギュラーなので正常系で設計する
