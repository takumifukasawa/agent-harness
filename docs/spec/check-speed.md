# check-speed — 検査が遅いことを実測で直す

状態: **A 完了。B は 1 件目（ハッシュのバッチ化）まで完了し、フル `check` は 95s → 62s**（2026-09-21）。B の続きと C は未確定。

## 目的

`harness check` は「完了の客観条件」なので、1 タスクにつき**実装役が 1〜2 回、統括が判定で 1 回、レビュアーも回す**。所要が長いほど、エージェントを使った開発全体が遅くなる。

2026-09-21 の実測（題材 cross-env のフェーズ 1、macOS Darwin 24.6 / arm64 / bash 3.2.57）:

| | 実測 |
|---|---|
| フル `harness check` | **約 1.5 分**（18 検査） |
| 実装役 1 体の所要 | sonnet で **6.3 分**（T03）・**7.6 分**（T04）、opus で **21.8 分**（T02） |
| レビュアー 1 体の所要 | **4.1 / 5.3 / 7.8 / 10.9 分**（観点 4 つ） |
| この題材でフル `check` が走った回数 | **12 回以上**（実装役 5 + 統括 5 + レビュアー数回）≒ **18 分超** |
| うち `tests/doctor.sh` 単体 | **約 58 秒**（44 シナリオ。2026-09-21、T05 の実装役が計測） |
| `--fast`（pre-commit のたびに走る分） | **1 秒**（11 検査。A の実測で判明） |

**A を実装して測った結果（2026-09-21、同じ機。フル 95 秒）**:

| 検査 | 秒 | 割合 |
|---|---|---|
| `doctor scenarios`（`tests/doctor.sh`） | **58s** | 61% |
| `update scenarios`（`tests/update.sh`） | **30s** | 32% |
| `stdin (curl \| bash) install` | 2s | |
| `seed checks are green` | 2s | |
| `init smoke test` | 2s | |
| 残り 13 件 | 合計 1s 程度 | |

**この 2 件で 93%。** 起票時の推定（`docs/tech-debt.md` #6）は `tests/doctor.sh` だけを挙げていたが、**`tests/update.sh` の 30 秒は #6 に記載が無かった**。測らずに #6 だけ返していたら、3 割を取り逃していた。

**`--fast` は 1 秒**なので、pre-commit のたびに走る分は無視してよい。むしろ **fast の印を増やす余地がある**（今 18 件中 11 件が fast）。 `docs/tech-debt.md` #6 は「`doctor` 呼び出し 1 回 ≒ 3 秒（外部コマンドを多数呼ぶ）」「T13 でフィクスチャ共有により 6m51s → 2m10s まで縮めたが、目標の 20〜40 秒には `doctor.sh` 側の最適化が要る」と書いているが、**これは Windows 機での起票時の見立て**で、今の macOS での内訳は測っていない。`harness check` は検査ごとの所要時間を出さないため、**どの検査が支配的かを誰も知らない**。

推定のまま最適化に入ると外す。前例がある: `docs/tech-debt.md` #3 は「macOS には `sha256sum` が無いはず」という走査結果を持っていたが、実測すると **Apple 提供のものが `/sbin/sha256sum` にあった**（外れ）。一方で走査に無かった `"$var日本語"` が 24 行あった（新発見）。**測ってから直す。**

## 進め方

**A（計測）を単独で終わらせ、その実測を見て B（返済）と C（並列化）の範囲を決める。** A は `harness/scripts/check.sh`（60 行）に数行を足す規模なので 1 タスクで終わる。

## 受け入れ条件

### A. 検査の所要時間が見える（今回の範囲）

- A1. `harness check` が**検査ごとの所要秒数**を出す
- A2. 総括行（`harness check: pass=... fail=... skipped=...`）に**合計時間**が出る
- A3. **遅い順の要約**が出る（上位いくつか。どれを削るか判断できる形）
- A4. `--fast`（pre-commit 経由）でも同じように出る。**コミットのたびに走る時間も見たい**
- A5. **macOS の素の bash 3.2 + BSD date で動く**。`date +%N`（GNU 拡張）や `date -d` に依存しない。Windows / Linux でも同じ形式で出る（決定 0006）
- A6. 既存の出力・判定・終了コードを壊さない（pass/fail の件数、失敗時の出力と直し方、exit code）
- A7. 計測のために検査 1 件あたり有意な遅延を足さない（プロセスを増やさない）
- A8. **実測結果を `docs/tech-debt.md` #6 に書き戻す**。推定（「doctor が重いはず」）を実測で置き換える

### B. 遅い検査を速くする（範囲は A の実測後に確定）

- B1. **対象は実測で確定した: `tests/doctor.sh`（58s）と `tests/update.sh`（30s）の 2 件で 93%。** 他の 16 件は合計 7 秒なので触らない
- B1a. **さらに一段測った結果（2026-09-21）、遅いのは診断そのものではなく「テストが作る使い捨てプロジェクト」だった**:

  | 操作 | 1 回 | `tests/doctor.sh` での回数 |
  |---|---|---|
  | `harness doctor` | **0.6s** | 13 |
  | `harness init` | **1.7s** | 15 |
  | `harness update` | **1.7s** | 27 |

  `tech-debt.md` #6 が前提にしていた「`doctor` 1 回 ≒ 3 秒」は**実測 0.6 秒**で覆った。**`doctor.sh` をいくら速くしても効かない。**
- B1b. **さらに測って打ち手が確定した（2026-09-21）。`init` 1 回が起動する外部プロセス**:

  | プロセス | 回数 |
  |---|---|
  | **`git hash-object`** | **71** |
  | `cp` | 74 |
  | `mkdir -p` | 43 |
  | その他（`grep` / `sed` / `node` / `awk` 等） | 25 程度 |

  ハッシュは `bin/harness:42` の `hash_file()` が**ファイルごとに `git hash-object` を起動する**形。同じ 82 ファイルを実測すると:

  | やり方 | 所要 |
  |---|---|
  | 1 ファイルずつ（今の実装） | **0.92s** |
  | まとめて 1 回（`git hash-object f1 f2 ...`） | **0.032s** |

  **29 倍の差。** `init` / `update` の 1.7 秒のうち**約 0.8 秒がハッシュのプロセス起動**で、計算そのものではない。
- B1c. **採る打ち手は (i)「`init` / `update` 自体を速くする」。** まず `git hash-object` をバッチ化する。テスト時間だけでなく**本番の `init` / `update` の体感も速くなる**。
  - **実施済み（`264892d`）。見込みと実績**: `init` 1.5s → **0.91s**、`update` 1.6s → **0.79s**、`status` 0.37s → **0.14s**。`git hash-object` の起動は init 1 回あたり **71 → 3**（ファイル数に比例しなくなった）。フル `check` は **95s → 62s（−35%）**。見込み（55s 前後）にはわずかに届かなかった
  - 実装は `git hash-object --no-filters --stdin-paths` を **1 プロセス常駐**させ、fifo でパスを送ってハッシュを受ける形。`--stdin-paths` を解さない git・`mkfifo` が無い環境・改行や CR を含むパスは**従来の 1 件ずつの経路に落ちる**。manifest はバイト単位で一致（差分は変更した CLI 自身の sha256 の 1 行のみ）
  - **残りの内訳（再計測、62s）**: `doctor scenarios` **43s** / `update scenarios` **15s** で依然 92%。ハッシュはもう支配要因ではない
  - `cp` 74 回・`mkdir -p` 43 回も同じ性質（プロセス起動が本体）。ハッシュを直した後に再計測して、次に何が支配的かを見る
  - (ii)（使い捨てプロジェクトの数を減らす）は (i) の後。**(i) はテストを一切変えずに効く**ので順序として先
- B2. **検査を弱めて速くしない**（`AGENTS.md`）。シナリオを削る・判定を緩めるのは不可。速くするのは実行の仕方
- B3. 目標値は A の実測を見て決める（#6 の起票時の目標は「20〜40 秒」だが、これも Windows 機での見立て）

### C. 並列実行（やるかどうかも A・B の後に決める）

- C1. B を終えてなお遅いときだけ検討する
- C2. **どの検査がなぜ落ちたかが読める**こと。出力が混線して原因が追えなくなるなら、速くても採らない

### D. 運用で減らす（コード変更ではない）

- D1. レビュー指摘の修正など、**独立した小さな修正は 1 タスクにまとめる**（1 件ずつタスクを切ると `check` がその回数だけ走る）。`task-orchestrate` の手順に落とす
- D2. **モデルを下げても壁時計時間は短くならない**（`docs/learnings.md` 2026-09-18 の実測）。速度目的でモデルを下げない

## 範囲外（やらないこと）

- **検査そのものを減らす・弱めること。** 遅いから削る、は `AGENTS.md` に正面から反する
- テストのカバレッジを下げること
- CI の導入（このハーネスは「git と bash だけ」が前提。決定 0001）
- A の段階で B・C に手を付けること（実測が出る前に直すと、何が効いたか分からなくなる）

## 未確定事項（人間の判断待ち）
